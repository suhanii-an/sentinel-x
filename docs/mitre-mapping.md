# MITRE ATT&CK mapping

## The rule: identifiers are authored, names are looked up

A rule file contains technique **IDs** and nothing else:

```yaml
mitre:
  techniques: [T1110, T1110.001]
  tactics: [TA0006]
```

The name "Brute Force" never appears in a rule file. It comes from the local
catalogue at render time. Two reasons, and the second is the one that matters:

1. A name written into a rule file drifts from the real one and nobody notices.
2. **An identifier that does not resolve is an error, not a guess.** Asking the
   API for a technique that is not in the catalogue returns a 404 whose message
   says so explicitly — it does not invent a plausible name. There is no code
   path anywhere in this project that fabricates a technique identifier.

## The catalogue

Generated by `scripts/build_mitre_catalog.py` into `data/mitre/`. It is a
**curated subset** of ATT&CK Enterprise: 14 tactics and 62 techniques covering
what this platform detects plus neighbouring techniques an analyst would expect
to see beside them.

The subset is stated wherever a coverage percentage appears, because a
percentage against a subset presented as a percentage against the full matrix
would be a flattering lie. The generator script documents the selection.

Bundling it locally rather than fetching at runtime means: no network dependency
in the detection path, reproducible builds, and no third-party service that can
change the platform's behaviour between deployments.

## Coverage

```
GET /api/v1/mitre/coverage
```

37 of 62 catalogued techniques are covered by an enabled rule.

The response leads with `uncovered_techniques`, and the Mitre page renders
uncovered techniques with the same visual weight as covered ones. A coverage
view that only lights up what you detect tells an analyst nothing about where
they are blind, which is the only question a coverage view is for.

Three states, and the third is the interesting one:

| State | Meaning |
|---|---|
| **Observed** | A rule covers it **and** it has appeared in a real incident here |
| **Covered** | An enabled rule maps to it; never yet seen |
| **Uncovered** | No rule covers it — a known gap |

A technique moves from "covered" to "observed" only when correlation actually
attributes it to an incident, so the matrix reflects what happened rather than
what was configured.

## From alert to attack chain

```
rule.mitre.techniques   →  alert.technique_ids
                        →  incident.technique_ids   (union across alerts)
                        →  catalog.tactics_for(...)  (IDs → tactics)
                        →  incident.attack_chain     (ordered by kill-chain phase)
```

The attack chain is the tactic-level reconstruction, ordered by when each tactic
*became detectable*. The incident timeline is the underlying evidence in strict
chronological order.

These can disagree — a persistence mechanism installed at 02:00 may not be
detected until an unrelated rule fires at 04:00 — and the API says which one
wins:

> *attack_chain is the tactic-level reconstruction, ordered by when each tactic
> became detectable. events is the underlying evidence in strict chronological
> order. Where they disagree, the events are authoritative.*

## Sub-techniques

Treated as first-class. A rule may map to `T1110.001` (Password Guessing)
without also claiming the parent, because the parent covers cases this rule does
not detect. Coverage counts both, and the matrix shows the relationship.

## Verified, not asserted

`tests/test_detection.py` walks every shipped rule and asserts that every
technique it references resolves in the local catalogue. A rule referencing an
invented identifier fails CI.

`tests/test_end_to_end.py` walks a real incident's mapped techniques and resolves
each one through the API, so the mapping is checked through the same path an
analyst uses rather than only in the rule file.
