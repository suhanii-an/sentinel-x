# Deployment

## What this is

SENTINEL-X is an educational security platform. It simulates attacks against its
own database and simulates responses against its own state.

It is **not** a production SOC, and this document is explicit about the gap
rather than leaving you to discover it. If you deploy it anywhere real, read the
"Before anything real" section first.

---

## Docker Compose

```bash
cp .env.example .env
python -c 'import secrets; print(secrets.token_urlsafe(48))'   # → SECRET_KEY
# also set POSTGRES_PASSWORD
docker compose up --build
```

Three services:

| Service | Role | Exposure |
|---|---|---|
| `db` | PostgreSQL 16 | **Not published to the host.** Nothing outside the compose network needs it, and a Postgres port on 0.0.0.0 is how development databases end up on the internet. |
| `api` | FastAPI | Internal only; reached through the proxy |
| `web` | nginx | The only published port (8080) |

On first start the API runs migrations, seeds a demo estate and prints the
generated admin password **once** in its logs. There is no default password
anywhere in this project. `--if-empty` means a restart never re-seeds over real
data.

Both images run as non-root with `no-new-privileges`. The backend image is
multi-stage, so the runtime layer carries no compiler and no build cache.

Same-origin by design: the browser talks only to nginx, which serves the console
and proxies `/api/`. There is no CORS configuration to get wrong and no
preflight surface.

## Local, without Docker

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

export DATABASE_URL="sqlite+pysqlite:///./sentinelx.db"
export SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"

python ../scripts/seed_database.py --quick
uvicorn app.main:app --reload
```

```bash
cd frontend && npm install && npm run dev
```

SQLite is a first-class supported target for local work and for the test suite.
Postgres is the production target.

## Configuration

Every setting is an environment variable. `.env.example` documents the full
surface. The ones that matter:

| Variable | Note |
|---|---|
| `SECRET_KEY` | **No usable default.** With `ENVIRONMENT=production` the application refuses to start without it rather than signing tokens with a well-known value. In development an ephemeral key is generated per process, so tokens do not survive a restart — which is the correct behaviour for a key nobody configured. |
| `DATABASE_URL` | Postgres in production, SQLite locally |
| `ENVIRONMENT` | `development` \| `test` \| `production` |
| `CORS_ORIGINS` | Irrelevant behind the bundled proxy; needed only if you serve the console from a different origin |
| `RATE_LIMIT_REQUESTS` | Per-caller general budget |
| `AI_RATE_LIMIT_REQUESTS` | AI endpoints get their own, much tighter budget |
| `AI_PROVIDER` | `none` by default. Everything works without it. |
| `DEMO_MODE` | Seeds a demo estate on first start; all of it flagged and labelled |

The sign-in throttle is deliberately **not** configurable. Rate-limiting
credential guessing is not something a deployment should be able to switch off.

## Migrations

```bash
alembic upgrade head              # apply
alembic check                     # models and migrations agree?
alembic revision --autogenerate -m "description"
```

`alembic check` runs in CI against Postgres. A model change with no migration
fails the build rather than the first real upgrade. Autogenerated migrations
import the project's custom timestamp type, so they run without hand-editing.

## Before anything real

The order here is the order of severity.

### 1. TLS

Terminate TLS at a proxy in front of nginx and enable HSTS — the header is
present in `frontend/nginx.conf`, commented, so it is a decision rather than an
oversight. Tokens over plain HTTP are tokens in the clear.

### 2. Keep `X-Forwarded-For` overwritten

The rate limiter keys on a client address that a **direct** connection can set
freely, so the API is safe only behind a proxy that *overwrites* the header
rather than appending to it. The bundled nginx does
(`proxy_set_header X-Forwarded-For $remote_addr`), but if you put your own proxy
in front, or expose the API directly, the sign-in throttle becomes bypassable
with one header and the audit log records an address the caller chose.

### 3. Move rate limiting to shared state before scaling out

Counters are in-process. `--workers 4` means four times the configured budget.
The limiter interface is small; backing it with Redis is the change. Until then,
run one worker and scale by adding instances behind a load balancer that also
fronts a shared limiter.

### 4. Know how revocation actually works

There is none, per token. Tokens are valid for `ACCESS_TOKEN_EXPIRE_MINUTES`
(eight hours by default) and there is no server-side deny list; signing out
clears the browser's copy and writes an audit entry, but the token itself keeps
working until it expires. Deactivating an *account* does take effect
immediately, because identity is re-resolved from the database on every request.

Rotating `SECRET_KEY` invalidates every issued token at once, which is the only
blunt instrument available. It is a restart with a new value, not an endpoint.
Lower the expiry if that window is too wide for your environment.

### 5. Ship the logs somewhere

The application emits one JSON object per line on stdout, already passed
through a redaction filter that scrubs bearer tokens, API keys, AWS access-key
IDs, JWTs and credential-shaped assignments. Ship stdout; do not write log files
next to the application.

### 6. Back up the database

Incidents, evidence and the audit trail live there and are not reconstructible.
The audit log is append-only by design, which is worth nothing if the volume is
ephemeral.

### 7. Set `ENVIRONMENT=production`

Beyond refusing to start without an explicit `SECRET_KEY`, this switches off
`/docs`, `/redoc` and `/openapi.json`. They publish the entire API surface and
every schema to an anonymous caller: exactly what you want while building, and
free reconnaissance in production.

### 8. Decide about `DEMO_MODE`

Leave it on and the platform seeds demo data, all of it flagged and labelled and
counted in `/system/info`. Turn it off for anything carrying real telemetry, so
the simulated share is zero rather than merely visible.

## Health and operations

```
GET /api/v1/system/health   # unauthenticated: an orchestrator needs it before a token exists
GET /api/v1/system/info     # authenticated: version, backend, rule count, simulated share, boundaries
```

`/health` reports only whether dependencies respond. No versions, no
configuration, nothing that helps somebody profile the deployment. Both
container images have a `HEALTHCHECK` wired to it.

`/system/info` is the honest one: it reports how many events are simulated, what
share of the total that is, and the list of things this platform is built never
to do.

## Scaling notes

Single-node by design. No clustering, no hot standby, no multi-tenancy.

The parts that would need attention first, in order:

1. **Rate limiting** → shared state (above).
2. **Detection on ingest** → a queue. Detection currently runs synchronously in
   the ingestion request. Fine at simulation volumes, wrong at real ones.
3. **Event table partitioning** → by time. The indexes are in place; the
   partitioning is not.
4. **Baseline computation** → a scheduled job. It is currently recomputed on
   demand.

None of these are hidden behind an abstraction that pretends they are solved.
